    Module 0Foundation

    The three shapes everything is made of

    Almost every confusion in this library is a shape confusion. There are only three objects in the whole pipeline. Learn them now and the other seven modules are just moving between them.

    E (n x d) the embedding matrix - one ROW per chunk, one COLUMN per dimension S (n x n) the similarity matrix - one cell per PAIR of chunks lam (n,) the spectrum - one number per independent DIRECTION embed multiply eigendecompose text ---------> E (n x d) ---------> S (n x n) ---------> lam (n,) | | +------------- SVD gives sigma ----------------+ (lam = sigma^2)
    Real world — a tasting panel

    Twenty wine critics each rate a wine on 384 descriptors. E is the scoresheet: one row per critic, one column per descriptor. S is "how much do critics agree with each other" — one number for every pair of critics. lam answers the real question: "we hired twenty critics, but how many genuinely different palates did we actually get?" If eighteen of them agree, you paid for twenty opinions and received three.

    That last question is the entire library. Swap "critics" for "context chunks" and you have it.

    Typical sizes: n is 20–500 context chunks, d is 384 for all-MiniLM-L6-v2. Keep in mind that n and d are independent — nearly every interesting property in this guide depends on which of the two is larger.

    The chain to memorise

    Unit-length rows → the diagonal of S is exactly 1 → trace(S) = n → the eigenvalues add up to n → lam/n is a probability distribution for free → Shannon entropy is well-defined with no fudge factor.

    Six links. If you remember one thing from this guide, remember that chain — it is why "normalize the rows" is not tidiness but the coordinate system the whole library is defined in.

    Module 1Implemented & tested

    Embeddings and cosine similarity

    Step 1An embedding is just a list of numbers

    A sentence encoder is a function. Text goes in, a fixed-length list of numbers comes out.

    "The Fed raised rates" ---> [0.021, -0.114, 0.087, ..., 0.052] 384 numbers

    That is the whole idea. The formal notation f: Σ* → R^d says exactly this and nothing more:

    • Σ* = "any string of any length"
    • R^d = "a list of d real numbers"
    • the arrow = "maps to"

    So read it as: text of any length in, always 384 numbers out. The "always" is the part that matters. Any sentence, any length, always 384. That is what lets you stack them into a rectangle.

    Why 384 numbers and not 1? One number can only place things on a line. Two numbers place them on a plane. 384 numbers give you 384 independent "directions of meaning", so "Fed raised rates" and "dog ate salmon" can be far apart in one direction while "Fed raised rates" and "central bank hiked" sit close together in that same direction. You need many dimensions to express "similar in this way, different in that way".

    Where the 384 numbers come from. The transformer produces one vector per token, so a 12-word sentence gives you roughly 12 vectors of 384 numbers each. Then it averages them into a single 384-vector. That averaging step — "mean pooling" — is what collapses the variable length into a fixed length.

    Real world — a colour swatch

    A paint colour is three numbers: R, G, B. "Similar colours" means "similar triples", and you can compute that without ever looking at the paint. An embedding is the same trick with 384 numbers instead of 3, and "meaning" instead of "colour". And just as (250, 20, 30) and (245, 25, 35) are both red, two paraphrases land at nearly the same 384 numbers.

    Trap — the geometry was trained in, not inherited

    This only works because the model was specifically trained so that "close together = similar meaning". Plain BERT, untrained for this task, is actually worse at sentence similarity than simply averaging word2vec vectors. Somebody had to train the nice geometry in, by showing the model millions of sentence pairs and pushing similar ones together. Use a non-sentence-tuned encoder with this library and the maths still runs perfectly while the results are meaningless.

    Step 2Stack the vectors into a spreadsheet

    You have 5 chunks of context. Embed each one and stack them as rows:

    dim0 dim1 dim2 ... dim383 chunk0 [ 0.021 -0.114 0.087 ... 0.052 ] chunk1 [ 0.019 -0.108 0.091 ... 0.048 ] chunk2 [-0.055 0.203 -0.011 ... 0.130 ] chunk3 [ 0.142 0.077 -0.220 ... 0.009 ] chunk4 [-0.031 -0.190 0.164 ... 0.071 ]

    Call this E. It is a spreadsheet: one row per chunk, one column per dimension. Shape (5, 384), written (n, d).

    Why rows = chunks and not columns = chunks? Three reasons, all pointing the same way:

    1. Speed. NumPy stores arrays row by row in memory. A whole chunk's 384 numbers sit side by side in RAM, so the CPU can slurp them in one go. Flip it and each chunk's numbers are scattered, and everything gets slower.
    2. Convention. Every stats textbook, every ML library, every SVD tutorial uses "rows = observations, columns = features". Go against it and you will be writing .T at every function call, and you will eventually get one wrong.
    3. We delete rows. Pruning means "throw away chunk 3". If chunks are rows, that is E[[0,1,2,4]] — one clean operation. If chunks were columns you would be transposing constantly.
    Real world — this is a returns matrix

    If you know finance, E is literally a returns or exposures matrix: 5 assets × 384 factor loadings. Same object, same linear algebra. Everything you know about correlation matrices, multicollinearity and factor risk transfers one-to-one — and I will keep cashing that in, because it is the fastest route to the intuition.

    Step 3Cosine similarity is just "what is the angle?"

    Two chunks are two arrows pointing out from the origin. Similar meaning means the arrows point the same way. So measure the angle between them.

    dot(a, b) cos(angle) = ----------------- |a| * |b| dot(a,b) = a[0]*b[0] + a[1]*b[1] + ... + a[383]*b[383] <- multiply pairwise, add up |a| = sqrt(a[0]^2 + ... + a[383]^2) <- the arrow's length (Pythagoras)

    Worked example in 2-D so you can picture it:

    a = [3, 4] b = [4, 3] dot(a,b) = 3*4 + 4*3 = 12 + 12 = 24 |a| = sqrt(9+16) = sqrt(25) = 5 |b| = sqrt(16+9) = sqrt(25) = 5 cos = 24 / (5*5) = 24/25 = 0.96 angle = 16.26 degrees

    Two arrows 16 degrees apart — nearly the same direction, so cosine 0.96, close to the maximum of 1.0. The scale:

    cos = +1.0 same direction identical meaning cos = 0.0 90 degrees apart unrelated cos = -1.0 opposite basically never happens in practice

    Drag the sliders. Watch what the length slider does and does not change — that is Step 4 in one gesture.

    Step 4Why divide by the lengths? The key design decision

    The dot product on its own equals |a| * |b| * cos(angle). It mixes together two different things: how aligned the arrows are, and how long they are.

    And here is the problem: embedding length correlates with chunk length. Longer text tends to produce a longer arrow. So if you rank by raw dot product, long chunks win just for being long.

    Verified — the long-document failure
    query = [1.00, 0.00] length 1.0 exact = [1.00, 0.00] length 1.0 short chunk, EXACTLY on topic longdoc = [3.00, 9.54] length 10.0 long chunk, mostly OFF topic raw dot cosine exact 1.00 1.000 longdoc 3.00 0.300 <-- raw dot ranks this FIRST

    Raw dot product claims the long off-topic chunk is three times better than the perfect match. Cosine correctly says 1.0 against 0.3. Dividing by the lengths is what throws away "how long is this chunk" and keeps only "which way does it point".

    Real world — keyword stuffing

    This is exactly the SEO trick of repeating a keyword two hundred times. Under a raw dot product, repetition inflates the score without adding meaning. Normalizing is the defence: it asks "what is this page about?" rather than "how much of this word is in it?"

    A second version: you would not judge two people's political views by how loudly they spoke. You would compare the direction of their opinions. Cosine measures direction; the dot product measures direction times volume.

    So we normalize once, up front. Divide every row by its own length:

    [3, 4] has length 5 ---> [3/5, 4/5] = [0.6, 0.8] length 1.0

    Now every chunk is an arrow of length exactly 1. Geometrically, every point has been pushed onto the surface of a sphere: same direction, all lengths equal to 1.

    And here is the payoff. If |a| = 1 and |b| = 1, the formula collapses:

    cos = dot(a,b) / (1 * 1) = dot(a,b)

    Once normalized, the dot product IS the cosine. No division ever again. That single fact is what turns the next step into one line of code.

    Bonus fact that kills a common interview debate

    People argue "cosine similarity or Euclidean distance?" For unit-length arrows there is nothing to argue about, because:

    distance(a,b)^2 = 2 - 2*cos(angle)

    As cosine rises, distance falls — always, smoothly. Sorting by cosine descending gives the identical ordering to sorting by distance ascending. They are the same ranking, not an approximation of one another. The debate only matters if you did not normalize.

    Step 5All pairs at once, with one multiply

    You want every pairwise similarity. The naive way is a double loop:

    for i in range(n):
    for j in range(n):
        S[i][j] = dot(E[i], E[j])     # slow Python, n^2 iterations

    But "dot every row with every row" is the definition of matrix multiplication. So:

    S = E @ E.T

    One line. Watch it happen with 3 chunks in 2-D:

    E = [[1.0, 0.0], chunk0 points right [0.8, 0.6], chunk1 points up-right [0.0, 1.0]] chunk2 points up E.T = [[1.0, 0.8, 0.0], same numbers, rows and columns swapped [0.0, 0.6, 1.0]] S = E @ E.T = [[1.0, 0.8, 0.0], [0.8, 1.0, 0.6], [0.0, 0.6, 1.0]]

    Check one entry by hand. S[1][2] should be chunk1 dotted with chunk2:

    S[1][2] = 0.8*0.0 + 0.6*1.0 = 0.6 <- matches

    Read the matrix:

    • S[0][0] = 1.0 — chunk0 against itself, always 1
    • S[0][2] = 0.0 — chunk0 points right, chunk2 points up, 90 degrees apart, unrelated
    • S[1][2] = 0.6 — chunk1 sits partway between, so moderately similar to both

    Shapes: (3,2) @ (2,3) -> (3,3). The inner 2 — the dimension count — is summed over and vanishes. You always land on (n, n), one similarity per pair.

    Two notes on the code. .T is free: NumPy copies nothing, it just relabels which direction is "rows". And @ means matrix multiply while * means multiply-each-cell-separately — using * here gives complete garbage, and on a square matrix it will not even raise an error.

    Step 6Four facts about S you should be able to recite

    S = [[1.0, 0.8, 0.0], [0.8, 1.0, 0.6], [0.0, 0.6, 1.0]]
    1. It is symmetric. S[i][j] == S[j][i], because the angle between a and b is the angle between b and a. Practical use: you only ever need half of it, so you can halve the memory or the work.
    2. The diagonal is all 1s. Every chunk is perfectly similar to itself.
    3. Therefore the diagonal adds up to n. Here 1+1+1 = 3. This sounds trivial. It is the most useful fact in the entire library, and Step 8 shows why.
    4. Eigenvalues are never negative (the "positive semi-definite" property). You do not need the proof, just the meaning: S is not an arbitrary grid of numbers, it is a geometrically realisable similarity structure. It could never claim "A is similar to B, B is similar to C, but A is the opposite of C" — that is impossible with real arrows, and non-negative eigenvalues are the maths enforcing it.
    Real world — a round-robin results table

    S is the grid you see in a league table where every team plays every other team. Symmetric (the A–B cell and the B–A cell are the same match), and the diagonal is meaningless-but-fixed (a team against itself). You never need both triangles, which is exactly why halving the memory is free.

    Step 7The bridge to SVD, in plain terms

    SVD takes your matrix E and says: "here are the main directions your data spreads out in, ranked most-important first." Each direction comes with a number — a singular value — saying how much data lies along it.

    The connection to what we just built:

    S = E @ E.T eigenvalues of S : [2.0, 1.0, 0.0] singular values of E : [1.414, 1.0] those squared : [2.0, 1.0] <-- SAME NUMBERS

    The eigenvalues of your similarity matrix are the squared singular values of your embedding matrix. Two views of one object. Module 1 and Module 2 compute the same thing from different angles, so nothing you build here gets thrown away.

    Also notice the third eigenvalue is 0. That is not a bug. We had 3 chunks living in 2 dimensions, so they cannot be independent — one is always expressible as a mix of the other two. A zero eigenvalue means "this direction contains nothing new".

    Generalise that: whenever you have more chunks than dimensions — more than 384 chunks, which in practice is always — some eigenvalues are mathematically guaranteed to be zero or near-zero. That is the precise statement of "your context window contains redundancy". It is not a hunch; it is forced by the shapes. Removing that guaranteed redundancy is exactly Module 2's job.

    Step 8Entropy: how many genuinely different things do I have?

    Here is the punchline of the whole library, and it is easier than it sounds. You have n chunks. But if three of them say the same thing, you do not have 3 pieces of information — you have 1. So: how many distinct things do you actually have?

    1. Get the eigenvalues of S: lam = [lam1, lam2, ..., lamN] 2. They add up to n (Step 6, fact 3), so divide by n to get numbers that add up to 1: p = lam / n 3. Feed p to Shannon entropy: H = -sum( p * log(p) ) 4. Turn entropy back into a count: effective rank = exp(H)

    Step 2 is free only because the diagonal of S is exactly 1, which is only true because we normalized in Step 4. That is why normalization keeps coming up — it is not tidiness, it is what makes this step work without fudging.

    Verified — three cases, real output
    Case 1: three chunks about totally different topics S = identity matrix eigenvalues = [1.0, 1.0, 1.0] spread evenly p = [0.333, 0.333, 0.333] H = 1.0986, exp(H) = 3.000 of 3 <-- "I have 3 distinct things" CORRECT Case 2: three IDENTICAL chunks S = all ones eigenvalues = [3.0, 0.0, 0.0] everything piled in one direction p = [1.0, 0.0, 0.0] H = 0.0, exp(H) = 1.000 of 3 <-- "I really only have 1 thing" CORRECT Case 3: two near-duplicates plus one unrelated eigenvalues = [1.971, 0.979, 0.05] p = [0.657, 0.326, 0.017] H = 0.7098, exp(H) = 2.033 of 3 <-- "about 2 distinct things" CORRECT

    Case 3 is the magic. It did not answer 2 or 3 — it answered 2.033, because the two near-duplicates are not exactly identical, so they count as slightly more than one thing. Entropy gives you a smooth, continuous count instead of a yes/no.

    The intuition behind the formula: -sum(p*log(p)) is largest when p is spread evenly and smallest when it is all piled into one spot. Even spread = many independent directions = lots of distinct information. All piled up = one direction = one thing said repeatedly. That is the entire concept.

    Real world — the effective number of bets

    Hold 50 technology stocks and you do not have 50 positions, you have about 3 — because they all move together. Portfolio managers compute this exact quantity and call it the effective number of bets or the diversification ratio. Same formula, same intuition. Pruning context by entropy is trimming a portfolio down to its genuinely independent risk factors.

    Step 9Why not just use a threshold?

    The obvious approach: "compute all the cosines, throw away anything above 0.8." Three problems.

    Problem 1: the number does not transfer. Your own encoder output proves it. The two near-duplicate Fed sentences are genuine paraphrases and they scored only 0.584:

    Verified — no single cutoff works
    threshold 0.9: catches 0 pairs threshold 0.8: catches 0 pairs <-- misses an obvious paraphrase threshold 0.7: catches 0 pairs threshold 0.5: catches 1 pair (0,1) <-- correct threshold 0.4: catches 3 pairs (0,1),(0,2),(1,2) <-- now over-pruning

    The "reasonable" 0.8 catches nothing at all. And whatever number you pick by trial and error is wrong for the next model, the next domain, and possibly the next document. You have hardcoded a magic constant fitted to one dataset.

    Problem 2: pairwise rules contradict themselves. Suppose:

    cos(A,B) = 0.85 -> too similar, drop one cos(B,C) = 0.85 -> too similar, drop one cos(A,C) = 0.60 -> fine, keep both

    So which do you drop? There is no right answer, and whatever your code does depends on loop order. A threshold rule looks at pairs. But redundancy is not about pairs — it is about the group. Entropy looks at the whole group at once and gives one consistent answer.

    Problem 3: entropy gives you a budget, not a filter. The real constraint is "I have 8000 tokens of room". Entropy lets you say "keep enough chunks to cover 95% of the distinct information". A threshold can only say "drop pairs above 0.8", and you discover afterwards whether you came in under budget. One is a resource allocation; the other is a guess.

    Trap — do not use the anisotropy argument here

    You will read that embeddings bunch into a narrow cone ("anisotropy"), so unrelated text scores 0.1–0.4 rather than 0. That research is about raw BERT and GPT-2, not sentence-tuned models. Our measured baseline for unrelated pairs is −0.001 to −0.12 — essentially orthogonal — because MiniLM was trained with in-batch negatives, which explicitly pushes unrelated pairs apart.

    Use the calibration argument instead: "an obvious paraphrase scored 0.584, so no fixed threshold generalises." It is stronger, and it is checkable in your own data.

    Step 10SVD vs PCA, without the jargon

    They are almost the same operation. The difference is one step:

    SVD on E -> finds the main directions, measured from the ORIGIN PCA on E -> subtracts the average first, then finds the main directions measured from the MIDDLE of the data

    We want SVD, with no subtracting. Two reasons that actually matter:

    Reason 1: it is a different question. PCA asks "which directions do the chunks vary in?" We want "which directions do the chunks occupy?" Those diverge in one important case: imagine a chunk sitting exactly at the average of all the others — the most boring, most redundant chunk possible. PCA subtracts the average, so that chunk becomes the zero vector, and PCA reports it as having no variance, which gets read as "unusual, keep it". Exactly backwards for our purpose.

    Reason 2: subtracting the average breaks the diagonal. Subtract the mean and the rows are no longer length 1, so the diagonal of S is not 1, so the eigenvalues do not sum to n, so Step 8's "divide by n" no longer produces a probability distribution, so entropy needs an arbitrary patch. One innocent preprocessing step and the clean maths three modules downstream falls apart.

    There is also a numerical reason worth knowing: PCA is often taught as "build the covariance matrix E.T @ E, then eigendecompose it". Building that product squares how badly conditioned your matrix is, costing you roughly half your decimal digits. SVD works on E directly and skips it. The rule to remember: never build a covariance matrix explicitly if you can SVD the data instead.

    The nuance if pressed: there is a real argument for centering. The single biggest direction in embedding data is often just "the average direction all text points in", carrying no useful signal — which is why techniques like all-but-the-top delete it deliberately. The complete answer is: "SVD on the uncentered matrix so the normalization invariant survives, but treat the top direction as a possible junk direction and test empirically whether dropping it helps." That says you know the theory, know the literature, and would measure rather than assert.

    Step 11The code, and the three lines people skip

    def l2_normalize(matrix, epsilon=1e-12):
    norms = np.linalg.norm(matrix, ord=2, axis=1, keepdims=True)
    return (matrix / np.maximum(norms, epsilon)).astype(np.float32, copy=False)

def cosine_similarity_matrix(vectors, assume_normalized=True):
    unit = vectors if assume_normalized else l2_normalize(vectors)
    gram = unit @ unit.T
    gram = np.clip(gram, -1.0, 1.0)      # 1
    gram = 0.5 * (gram + gram.T)         # 2
    np.fill_diagonal(gram, 1.0)          # 3
    return gram.astype(np.float32, copy=False)
    LineLooks likeActually prevents
    keepdims=Truea formatting flag shape (n,1) broadcasts per row. Without it you get (n,), which NumPy right-aligns and divides column-wise. Raises when n≠d — and silently computes garbage when n=d, entirely possible at d=384.
    np.maximumthe same as norms+eps a floor, not a bias. Adding epsilon perturbs every row's scale; maximum is a no-op on real norms and only guards genuine zeros.
    clip (#1)paranoia float32 error over 384 terms puts the diagonal at 1.0000001. Anything calling arccos downstream returns NaN and poisons everything after it.
    0.5*(S+S.T) (#2)a no-op on a symmetric matrix BLAS sums S[i][j] and S[j][i] in different orders, and float addition is not associative, so they can differ in the last bits. eigvalsh assumes exact symmetry.
    fill_diagonal (#3)cosmetic this is what makes trace(S) = n exact, which is what makes Step 8's probability distribution exact. Drift here is a systematic error that grows with n.

    RecapModule 1 in one paragraph

    Text goes in, 384 numbers come out per chunk. Stack them as rows into E. Divide each row by its own length so every chunk is an arrow of length 1 — this makes similarity depend on direction only, not chunk length, and it makes the dot product equal the cosine. Then S = E @ E.T computes every pairwise similarity in one multiply. S is symmetric with 1s on the diagonal, so its eigenvalues add up to n, so dividing by n gives a probability distribution for free, so Shannon entropy tells you how many genuinely distinct things you have — a continuous count, which is what you prune against. And those same eigenvalues are the squared singular values of E, which is Module 2's input. Nothing gets recomputed.

    Self-test — Module 1answer aloud, then open
    Why L2-normalize at the embedding boundary instead of inside the cosine function where it is needed? Answer

    Three reasons, increasing in importance.

    Correctness. It becomes an enforced invariant of the type rather than a precondition every caller must remember. EmbeddingMatrix validates it once at construction, so no downstream function can silently receive raw vectors.

    Performance. Normalizing is O(nd) and cosine is called repeatedly — O(n) times in a greedy pruner — so normalizing per call turns a one-off into O(n²d) of duplicated work. It also lets the matmul drop every division.

    The real reason: the maths downstream depends on it. Unit rows put exact 1s on the diagonal, so eigenvalues sum to exactly n, so lam/n is a probability distribution, so Shannon entropy is well-defined with no fudge factor. Normalization is the coordinate system, not a preprocessing step. I keep an assume_normalized=False escape hatch so the API stays honest about its precondition.

    10,000 chunks, 384 dimensions. Walk me through all pairwise cosines. What breaks? Answer

    Normalize rows once, then one GEMM: S = E @ E.T. Work is n*n*d = 3.8e10 multiply-adds — under a second on a GPU, a few seconds on CPU BLAS.

    Compute is not the constraint; memory is. S is 1e8 float32 entries = 400 MB. At n=100,000 it is 40 GB and does not fit. The method is O(n²) in space and simply stops working.

    Fixes, cheapest first: (a) store only the upper triangle — 2×, does not change the asymptote; (b) never materialize S — stream it in row blocks and reduce each block immediately to the statistics you need (row-mean, row-max), giving O(nb) memory in one pass — this is the fix that matters; (c) replace exact all-pairs with ANN search (HNSW, FAISS) keeping a sparse k-NN graph, turning O(n²) into about O(nk log n); (d) for the spectral path skip S entirely — randomized truncated SVD runs on E at O(ndk), linear in n.

    I would also flag dtype: float32, because the encoder's own noise is ~1e-3, so float64's extra digits are meaningless while doubling the memory bandwidth that actually bottlenecks a GEMM of this shape.

    A colleague ships E / np.linalg.norm(E, axis=1). Tests pass. What did they break?Answer

    They dropped keepdims=True, so norms is (n,) instead of (n,1). NumPy broadcasting aligns from the trailing axis, so (n,d) / (n,) is read as dividing by a row vector — it normalizes down columns, not across rows.

    Why tests passed: when n != d this raises a ValueError and you catch it at once. The danger is n == d — perfectly possible, since d=384 and you might have 384 chunks — where it silently succeeds and returns wrong numbers. Rows are no longer unit length, so the diagonal is not 1, the trace is not n, and every entropy number downstream is quietly wrong.

    The lesson: assert the invariant, do not merely compute it. Our EmbeddingMatrix.__post_init__ would have caught this at construction.

    Quant framing: how is S different from a correlation matrix, and how does it fail? Answer

    Structurally it is the same object — symmetric, PSD, unit diagonal, trace n. The only difference is that correlation centers the columns first and this does not. So the same diagnostics apply: eigenvalue spectrum, condition number, effective rank.

    And it fails the same way, which is the failure that wrecks naive risk models: the matrix is estimated, not observed. When n is comparable to d, the small eigenvalues are estimation noise, and anything that inverts the matrix or leans on its bottom directions is fitting noise. Marchenko–Pastur tells you where the noise bulk ends as a function of n/d, which is a principled place to truncate.

    The reassuring part: this pruner only ever reads the top of the spectrum and discards the bottom — the numerically safe direction, the same logic as covariance shrinkage or using a factor model instead of the sample covariance. We never invert.

    The text-specific failure: absolute similarity levels are not interpretable — our own paraphrases scored 0.584 — so only relative structure is actionable.

    Module 2Theory ahead of code

    SVD and subspace decomposition

    Cosine tells you about pairs. SVD tells you about the collection: which directions of meaning your context actually occupies, and how much of it sits along each one.

    Step 1What SVD is actually doing

    Here is the one-sentence version: SVD finds the handful of directions your data really lives in, sorted from most-used to least-used.

    Picture 500 dots scattered on a sheet of paper. They look like a cloud, but you notice they form a long thin cigar shape pointing north-east. SVD finds that: "direction 1 is north-east and most of your data is spread along it; direction 2 is north-west and there is only a little spread along that". Two directions, ranked, with a number for each.

    Now do that in 384 dimensions instead of 2, and the dots are chunks of text. Same operation.

    Real world 1 — a graphic equaliser

    Think of the sliders on a stereo equaliser: bass, mid, treble, and so on. Any song is a mix of those bands, each with its own level. SVD does the same thing to your context: it breaks it into "bands of meaning", each with a volume level (sigma). Truncating the SVD is turning off the quietest bands — the song still sounds like the song.

    Real world 2 — JPEG compression is literally this

    A JPEG works by decomposing an image into patterns ranked by how much they contribute, then throwing away the small ones. A 10× smaller file still looks like the photo, because most of the information really was in a few big components.

    That is exactly what we are doing to a context window. The image analogy is worth holding onto, because it makes the key question obvious: how far can you compress before it starts to look wrong? That question is Module 6.

    Real world 3 — equity factor models

    You hold 500 stocks. You do not have 500 independent bets — you have maybe five: market, size, value, momentum, quality. Everything else is those five in combination plus noise. Running SVD on a returns matrix is how you find those factors without being told they exist.

    Same operation, same matrix shape, same interpretation. Our sigma_1 direction is the "market factor" of your context: the theme everything shares.

    Step 2The three matrices, and what each one is

    E = U Sigma V.T E (n x d) your data U (n x r) how much each CHUNK uses each direction ("chunk coordinates") Sigma (r x r) diagonal, sigma_1 >= sigma_2 >= ... >= 0 ("how much is there") V.T (r x d) the DIRECTIONS themselves, in meaning-space ("semantic axes") r = min(n, d) for the thin SVD

    Read it right to left, the way the matrices act on a vector: V.T rotates into a new set of axes, Sigma stretches each axis by a different amount, U rotates into the output space. Rotate, stretch, rotate. Only the stretch destroys anything — and a sigma of zero destroys an entire direction.

    Of the three, V is the one to picture. Each column of V is a direction in 384-dimensional meaning-space that your context uses, and sigma_i says how heavily. If your 50 chunks are all about the Fed, sigma_1 is huge and everything after it is near zero.

    Step 4Eckart–Young: truncation is provably optimal

    Keep only the top k directions and you get E_k. The theorem says something remarkably strong: of all matrices of rank k, E_k is the closest one to E — in both the Frobenius and spectral norms. Not a heuristic. Optimal. And the error has a closed form:

    ||E - E_k||_F = sqrt( sigma_{k+1}^2 + sigma_{k+2}^2 + ... + sigma_r^2 ) the error is exactly the square root of the energy you threw away

    Why this matters so much: it turns "which information should I discard?" from a judgement call into a solved problem, and it tells you the cost before you pay it. No greedy feature-selection scheme gives you both.

    Check it on the example above:

    Step 6Randomized SVD, and why it is not cheating

    Full SVD costs O(n d min(n,d)) and computes all r directions. We only ever want the top k. The randomized algorithm:

    1. draw a random Gaussian matrix Omega (d x (k+p)) p = oversample, ~5-10 2. sample the range Y = E @ Omega (n x (k+p)) 3. orthonormalize Q = qr(Y).Q spans ~the top-k range of E 4. project into that small basis B = Q.T @ E ((k+p) x d) <- tiny 5. exact SVD of the small matrix B = U_b Sigma V.T 6. lift back U = Q @ U_b cost O(n d k) instead of O(n d min(n,d)) -- LINEAR in n
    Real world — exit polling

    You do not interview all 40 million voters to call an election. You sample a few thousand at random, and because the dominant patterns are dominant, a random sample finds them reliably. Randomized SVD is the same bet: multiply by a random matrix and you almost surely land in the subspace where most of the energy is, because the large singular directions dominate the product.

    The error bound is probabilistic but extremely tight, and oversampling by ~10 makes failure vanishingly unlikely. This is the standard industrial tool, not an approximation of last resort.

    RecapModule 2 in one paragraph

    SVD factors E into rotate–stretch–rotate: U says how much each chunk uses each direction, Sigma says how much is there, and V holds the directions themselves. Identical chunks get identical rows in U, and a direction used by two chunks gets sigma² = 2 — which is why the spectrum measures redundancy. Eckart–Young guarantees that keeping the top k directions is the optimal rank-k summary, with error exactly sqrt(dropped sigma²). The eigenvalues of Module 1's S are these sigma² values, so nothing is recomputed. At scale, use randomized SVD for O(ndk) instead of building S at all. And watch the cumulative energy curve: a flat spectrum is the system telling you there is little redundancy to remove.

    Module 3Theory ahead of code

    Shannon entropy and effective rank

    Step 1The question this module answers

    You have n chunks. If three of them say the same thing, you do not have three pieces of information — you have one. So: how many genuinely distinct things do you actually have?

    Notice this is a counting question, and the honest answer is usually not a whole number. Two chunks that are 90% the same are more than one thing and less than two. We want a count that can say "2.03".

    Real world 1 — the dinner party

    Ten guests at dinner. Eight of them are from the same family, have the same job, and tell the same three stories. The other two are a marine biologist and a jazz drummer.

    How many conversations did you actually host? Not ten. Roughly three: the family, the biologist, the drummer. You invited ten people and received three perspectives. Effective rank computes that number.

    Real world 2 — the playlist

    A 100-song playlist where 60 songs are the same artist and the other 40 are 40 different artists. How varied is it really?

    Run the numbers and the answer is around 8.6, not 41 and not 100 — because the one dominant artist eats most of the "weight" while the 40 one-offs each contribute a little. That is the shape of nearly every retrieved context window: one dominant theme plus a long thin tail.

    Step 2First, turn eigenvalues into probabilities

    Shannon entropy is defined on a probability distribution — a list of non-negative numbers that add up to exactly 1. Our eigenvalues are non-negative (Module 1, fact 4), but they add up to n, not 1.

    So divide by n:

    p = lam / n

    That is the entire conversion, and it works only because trace(S) = n exactly, which is true only because we normalized the rows in Module 1. This is the payoff of that invariant. Had we centered the data, or skipped normalization, or let float error drift the diagonal, this line would need an arbitrary patch and the numbers below would stop meaning anything.

    Step 3What Shannon entropy actually measures

    H = -sum( p_i * log(p_i) )

    Ignore the formula for a second. Entropy answers: "how surprised am I, on average, by a draw from this distribution?"

    • A coin that always lands heads: zero surprise. H = 0.
    • A fair coin: maximum surprise for two outcomes. H = log(2).
    • A fair 6-sided die: more outcomes, more surprise. H = log(6).
    • A loaded die that shows 6 ninety percent of the time: back down near zero, because you can nearly always guess.

    So entropy is largest when the distribution is spread evenly and smallest when it is concentrated in one place. Translate to our setting: evenly spread eigenvalues mean many independent directions of meaning; all the weight on one eigenvalue means one direction, i.e. one thing said over and over.

    Why the minus sign and the log? Probabilities are below 1, so their logs are negative; the minus sign makes H positive. The log is there because information is multiplicative while we want to add it — two independent fair coins have 4 outcomes, and log(4) = log(2) + log(2). The log turns "multiply the possibilities" into "add the information".

    Step 4Compute it by hand, once

    Do this once with a pen and the formula stops being intimidating. Suppose three directions with p = [0.5, 0.3, 0.2]:

    step 1 - take each log: ln(0.5) = -0.693147 ln(0.3) = -1.203973 ln(0.2) = -1.609438 step 2 - multiply each by its own p: 0.5 * -0.693147 = -0.346574 0.3 * -1.203973 = -0.361192 0.2 * -1.609438 = -0.321888 step 3 - add them up: -0.346574 + -0.361192 + -0.321888 = -1.029654 step 4 - flip the sign: H = 1.029654 nats step 5 - exponentiate to get a count: exp(1.029654) = 2.800

    So a spectrum of [0.5, 0.3, 0.2] behaves like 2.8 distinct things, not 3. The 0.2 direction is real but carries less weight, so it counts as less than a full item.

    Notice in step 2 that all three contributions were roughly equal (−0.35, −0.36, −0.32). That is not a coincidence: the term p*log(p) is small both when p is tiny (nothing there) and when p is near 1 (no surprise), peaking in the middle. Middling directions contribute most to entropy.

    Step 5Why exponentiate? Because it gives a count

    Here is the proof, and it is three lines. Suppose m directions share the weight equally and the rest are zero. Each p_i = 1/m, so:

    H = -sum_{i=1..m} (1/m) * log(1/m) = -m * (1/m) * log(1/m) m identical terms = -log(1/m) = log(m) exp(H) = exp(log m) = m

    A uniform spectrum over m directions returns exactly m. So exp(H) is measured in the same units as "number of things". Because entropy is maximised by the uniform distribution and minimised by a concentrated one, exp(H) slides smoothly between 1 and n. It is a continuous relaxation of matrix rank — equal to the rank when the spectrum is flat, strictly less whenever the weight is unevenly spread.

    That continuity is what makes it usable as an objective. Integer rank has no gradient; you cannot optimise against it. exp(H) you can.

    Step 6Turning effective rank into a decision

    Knowing you have "15.9 distinct ideas in 20 chunks" is only useful if it sets k. Three defensible rules:

    RuleHowTrade-off
    Energy threshold k = smallest k where cumulative sigma² ≥ 95% Simple and standard, but 95% is itself a magic constant — just a far better-behaved one than a cosine cutoff, because it is scale-free and means the same thing on any matrix.
    Effective rank k = ceil(exp(H)) Fully tuning-free and rotation-invariant. Can over-keep when the tail is long and flat, since many tiny eigenvalues still raise H.
    Noise floor Marchenko–Pastur: keep only eigenvalues above the random-matrix bulk edge, which is a function of n/d The most principled — it asks "is this direction distinguishable from noise at all?" Needs n and d and assumes the noise model roughly holds.
    Real world — the rotation-invariance point, concretely

    Swap MiniLM for a different encoder and every cosine value changes, so every threshold you tuned is now wrong. But H depends only on eigenvalues, and eigenvalues do not change when you rotate the coordinate system. So "this context has ~16 distinct ideas" survives the encoder swap; "drop pairs above 0.8" does not.

    Think of it like measuring a room's volume in litres versus describing it as "three paces by four paces". One transfers; the other depends on your legs.

    Trap — two ways to get entropy wrong in code

    1. Nats versus bits. log base e gives nats; base 2 gives bits. It does not matter for exp(H) provided you are consistent (2**H_bits == exp(H_nats)), but quoting "H = 2.77" with no unit is the kind of thing an interviewer picks at. We use nats because np.log is the natural log and exp inverts it directly.

    2. 0 * log(0). That is 0 * -inf = NaN in floating point. The mathematical limit is 0, so you must mask zeros (p[p > 1e-12]). This is not hypothetical: any corpus with n > d has exact zero eigenvalues, so an unmasked implementation returns NaN on every realistic input.

    RecapModule 3 in one paragraph

    Eigenvalues sum to n, so p = lam/n is a probability distribution for free. Shannon entropy H = -sum(p log p) measures how evenly that weight is spread: maximal when every direction matters equally, zero when one direction has everything. Exponentiating converts it back into a count, and for m equally-weighted directions exp(H) is exactly m — so effective rank is a continuous version of matrix rank, which is what makes it optimisable. It is unitless, needs no tuning, and is invariant to rotations of the embedding space, so it transfers across encoders where a cosine threshold cannot. Mask the zeros or you will get NaN.

    A PM says "just keep the top 10 chunks by relevance." Why is that different, and when are they right? Answer

    Relevance ranking is a pointwise criterion: it scores each chunk against the query independently. The failure is that the top 10 by relevance are frequently near-duplicates — they all answer the same facet, because whatever makes one relevant makes its paraphrase relevant too. You spend the whole budget re-reading one idea and drop the chunk covering the second facet.

    When the PM is right: when the corpus has little redundancy, the relevance ranking is already near-diverse and the extra machinery buys nothing but latency.     The pruning engine

    Modules 1–3 score. This module chooses. You have a token budget; which chunks survive? That is a combinatorial optimisation problem with its own theory, and it carries the strongest software-engineering signal in the whole project.

    Step 1This is a coverage problem, not a filtering problem

    The instinct is to filter: walk the list, throw out anything too similar to what you already have. That instinct is wrong, and naming why is the point of this module.

    The right framing: every chunk you throw away should still be well-represented by something you kept.

    Real world 1 — packing a suitcase

    One bag, a weight limit, a two-week trip. You do not pack "everything that is not too similar to what is already in the bag" — you pack so that every situation you might face is covered: something warm, something smart, something waterproof, shoes.

    Five identical black t-shirts fail not because they are similar to each other, but because they leave the "it rained" situation uncovered. The criterion is coverage of what you left at home, not dissimilarity within the bag.

    Real world 2 — where the name comes from

    The formal name for this objective is facility location, and it is literal: where do you put k fire stations so that every house in the city is close to one? You do not place stations far apart for its own sake; you place them so no house is far from help.

    Swap "house" for "chunk you dropped" and "close to a station" for "similar to a chunk you kept", and it is exactly our problem. Same maths, decades of existing theory, which is why we do not have to invent anything.

    Step 2Write the objective down

    maximize f(P) = (1/n) * sum over all i in A of ( max over j in P of S[i][j] ) subject to sum of tokens(j) for j in P <= budget A = the full active set P = the kept subset

    Read the inner term slowly, because it is the whole idea. For chunk i, find its best representative among the chunks you kept:

    • If i itself was kept, that is 1.0 — perfect representation.
    • If i was dropped but a near-duplicate survived, it is still high. Nothing was really lost.
    • If i was dropped and nothing like it survived, it is low, and the objective punishes you.

    Then average over all chunks. A high score means "I could delete most of this context and still have something standing in for everything I deleted."

    Step 3Diminishing returns, and why they matter

    The objective has a property with a fancy name and a simple meaning.

    Real world — the second slice of pizza

    The first slice, when you are starving, is worth a lot. The fourth is worth less. The eighth might be worth nothing. The value of adding one more shrinks as you already have more.

    That is submodularity. Formally: for P a subset of Q, adding x helps P at least as much as it helps Q:

    f(P + x) - f(P) >= f(Q + x) - f(Q)

    Our objective has it because the inner term is a max: once some kept chunk already represents i well, a second similar chunk adds almost nothing. Here it is in real numbers — the value of adding chunk 2 (a monetary-policy paraphrase) to sets of increasing size:

The gain then plateaus, because the remaining picks are from other topics and do not compete with chunk 2 at all. The numbers never increase. That is submodularity, observed rather than asserted.

    Step 4Greedy, and why it is provably good enough

    Finding the genuinely optimal subset is NP-hard — you would have to check every combination. But our objective is monotone (adding a chunk never hurts) and submodular (diminishing returns), and for that class there is a theorem.

    The Nemhauser–Wolsey–Fisher result: plain greedy selection — repeatedly take whichever chunk adds the most right now — achieves at least (1 - 1/e) ≈ 63.2% of the optimum. And that bound is tight: no polynomial-time algorithm does better in general unless P = NP.

    The money answer in an interview

    "The problem is NP-hard, but the objective is monotone submodular, so greedy is a 1 - 1/e approximation by Nemhauser–Wolsey–Fisher, and that bound is tight."

    That single sentence says you recognised the problem class, know the guarantee, and know not to waste time hunting for something better. Most candidates either brute-force it or hand-wave "greedy seems fine".

    greedy: P = {} while budget remains: pick the chunk x maximizing f(P + x) - f(P) <- marginal gain P = P + x cost O(k * n^2) with a running-best array -- trivial for n in the hundreds

    3. Picks 6, 7 and 8 are all "unrelated" chunks — the dog, the kitchen cabinets, the hiking trail. They are the most distinct chunks in the corpus, so pure coverage loves them.
    Trap — our own output shows the flaw

    Spending three of eight slots on the dog, the cabinets and the hiking trail is almost certainly wrong for a real query about monetary policy. Pure facility location maximises diversity and knows nothing about the query — so the most irrelevant chunk in your corpus is also the most diverse, and it gets rewarded for it.

    This is not a bug in the implementation; it is the objective doing exactly what it was asked. It is also precisely why MMR exists. If you present facility location in an interview without volunteering this limitation, a good interviewer will find it for you.

    Step 6MMR: folding relevance back in

    Maximal Marginal Relevance fixes Step 5's flaw by interpolating between "is this relevant to the query?" and "is this different from what I have?":

    pick next x = argmax [ lambda * rel(x, query) - (1 - lambda) * max_{j in P} S[x][j] ] lambda = 1.0 -> pure relevance (top-k; ignores redundancy entirely) lambda = 0.0 -> pure diversity (ignores the query entirely - the dog problem) lambda ~ 0.7 -> typical starting point. TUNE IT, do not inherit it.
    Real world — a streaming service's front row

    If a recommender showed you the ten films closest to your taste, you would get ten near-identical thrillers. Every serious recommender therefore diversifies on purpose — and MMR is one of the standard ways. It is also why search results deliberately mix a news result, a video, and a reference page rather than ten variations of the top hit.

    lambda is an honest hyperparameter: it encodes a real preference about the relevance/diversity trade-off that no amount of maths can settle for you. That is categorically different from a cosine cutoff, which is a magic constant standing in for a measurement nobody made. Being able to draw that distinction is worth more than either number.

It covered policy and earnings and never reached risk, ML, or the unrelated chunks at all. Not because it judged them unimportant, but because it ran out of budget before it got to them.

    Threshold dedup is not a diversity algorithm. It is a scan that rejects anything too close to what it has already taken, so whatever comes first wins and whole regions of meaning-space are never visited. Greedy beat it on both coverage and retained effective rank at every cutoff tested, and it is not close.

    The general principle: a filter has no notion of what it has failed to cover; an objective does.

    Trap — token budgets break the clean guarantee

    The 1 - 1/e bound is for a cardinality constraint ("keep at most k items"). A real token budget is a knapsack constraint — items have different costs — and plain greedy loses the guarantee there.

    The fix is cost-benefit greedy: rank by marginal_gain / token_cost rather than marginal gain alone, which recovers a (1 - 1/e)-style bound (Sviridenko; Khuller–Moss–Naor). Knowing that the constraint type changes the guarantee is exactly the depth a good interviewer is probing for.

    RecapModule 4 in one paragraph

    Redundancy removal is a set-selection problem, not a filtering problem: the objective is facility location, "every chunk I dropped should still be represented by something I kept". That objective is monotone and submodular — diminishing returns, which we measured dropping 4.6× the moment a same-topic chunk entered the set — so greedy selection is provably within 1 - 1/e of optimal, and that bound is tight. Watching it run, it jumps topics on its own because a cluster's marginal gain collapses after its first pick: diversity is emergent, not programmed. Its weakness is that it knows nothing about the query, which is why it spent three of eight slots on the most irrelevant chunks available; MMR fixes that by interpolating with a relevance term. And a real token budget is a knapsack, not a cardinality constraint, so rank by gain-per-token to keep the guarantee.

    Self-test — Module 4answer aloud, then open
    Define submodularity and explain why it makes greedy the right choice.Answer

    A set function f is submodular if for any P ⊆ Q and element x outside Q:

    f(P + x) - f(P) >= f(Q + x) - f(Q)

    Diminishing returns: an element contributes more to a small set than to a large one. Our coverage objective has it because the inner term is a max — once some chunk already represents i well, a second similar chunk adds little. I measured it: adding a policy chunk to the empty set gained 0.1517, but only 0.0327 once another policy chunk was present.

    Why greedy: the exact problem is NP-hard, but for monotone submodular f under a cardinality constraint, Nemhauser–Wolsey–Fisher guarantees greedy reaches at least (1 - 1/e) ≈ 63.2% of the optimum, and that factor is tight. So greedy is not a shortcut I am apologising for — it is the best guarantee available, at O(k n²).

    I would add that a real token budget makes it a knapsack constraint, which breaks the plain bound; ranking by gain / token_cost restores a comparable one.

    Threshold dedup and greedy both kept 8 chunks. Greedy scored 0.640 vs 0.507. Explain the mechanism, not the number. Answer

    They optimise different things. Threshold dedup is a sequential filter: it walks the list in whatever order it arrives and rejects anything too similar to something already accepted. The outcome is therefore a function of arrival order, not of the set's structure.

    In our corpus, chunks are grouped by topic, so at threshold 0.70 the filter accepted [0..7] — it filled the entire budget from the first two topics and never examined risk methodology, ML methodology, or the unrelated chunks. It did not judge them unimportant; it ran out of budget before reaching them.

    Greedy optimises a global set objective. At each step it asks "which chunk most improves representation of everything I am not keeping?" — so after taking one policy chunk, every other policy chunk's marginal gain collapses and a risk chunk becomes the best pick. The trace shows it alternating earnings → risk → policy → earnings → method, landing in every cluster.

    The general lesson: a filter has no notion of what it failed to cover; an objective does.

    Your greedy pruner spent 3 of 8 slots on a chunk about a dog, one about cabinets, and one about hiking. Defend or fix it.Answer

    I would not defend it — it is the objective working correctly and the objective being wrong for the task.

    Facility location maximises coverage of the corpus and contains no query term at all. The most irrelevant chunk in the corpus is by construction the most distinct one, so pure diversity rewards it. Our trace shows exactly that: picks 6, 7 and 8 were the three unrelated chunks, because after covering the four real topics they had the highest remaining marginal gain.

    The fix is MMR — add a relevance term and interpolate: lambda * rel(x, query) - (1-lambda) * max_sim. With lambda around 0.7 the dog chunk's near-zero relevance kills it despite its high distinctness.

    The deeper point I would make: pure diversity is never the real objective. Nobody wants a maximally varied context, they want the most useful context under a budget. Diversity is a corrective applied to relevance, not a goal in itself. Presenting facility location without that caveat would be presenting half the method.

    Your pruner drops the one chunk containing the fact the user needed. How do you respond? Answer

    I would separate two failure modes, because they have different fixes.

    Mode 1: the objective was right and the chunk was genuinely redundant, but the representative we kept did not carry that specific fact. This is the real limitation. Coverage is measured in embedding space, and embeddings capture topical similarity, not factual equivalence. "Rates rose 25bp" and "rates rose 50bp" are nearly identical vectors and completely different facts. No amount of spectral machinery fixes that, because the signal is not in the geometry. Mitigations: never prune below a floor; preferentially keep chunks carrying numbers or named entities; prune only chunks above a redundancy threshold rather than everything.

    Mode 2: we pruned when we should not have pruned at all. If the retrieved set's effective rank is already close to k, there is no redundancy to remove and pruning is pure downside risk. The system should measure that and decline — "this context is not redundant" is a valid output.

    And the honest framing: this is why the evaluation harness is not optional. Without measuring compression against task accuracy, "my pruner preserves quality" is unfalsifiable. The defensible position is a measured operating point — "at 50% token reduction we lose 1.2% answer accuracy" — not an argument from theory.

    Chunking and the input layer

    Every module so far assumed "chunks" existed. They do not — you make them, and that choice quietly decides how well everything downstream works. This is the least mathematical module and the one most likely to hold your real wins.

    Step 1Why chunk size is the whole problem

    SMALL chunks (1-2 sentences) LARGE chunks (paragraphs) + precise similarity + self-contained and readable + fine-grained pruning + fewer chunks -> cheaper n^2 - lose surrounding context - similarity gets mushy - pronouns dangle ("it rose") - pruning is all-or-nothing - n explodes -> n^2 hurts - one vector has to cover several ideas
    Real world — cutting a documentary

    Cut every 30 seconds regardless of content and you get clips that start mid-sentence and end mid-thought — useless on their own. Cut at scene boundaries and every clip stands up by itself. Fixed-size chunking is cutting on a stopwatch; structural chunking is cutting on scenes.

    Step 2The deeper problem: mean pooling averages ideas

    Remember from Module 1 that a chunk's embedding is the average of its token vectors. So a paragraph covering three topics produces a vector pointing somewhere between all three — a centroid that matches nothing well.

    Real world — averaging two photographs

    Average a photo of a forest with a photo of a beach, pixel by pixel. You do not get "nature". You get brown-grey mud that looks like neither.

    That is what happens to a chunk covering several topics. And it gets worse: because every long chunk drifts toward the corpus average, all long chunks drift toward each other. Your pairwise cosines creep upward and compress into a narrow band, so discrimination collapses. This is a direct argument for chunks smaller than intuition suggests: roughly one idea per chunk, because one idea is what a single vector can faithfully represent.

    Step 3The four strategies, worst to best

    StrategyMechanismVerdict
    Fixed character countsplit every N characters Splits mid-word and mid-sentence. Acceptable only as a baseline to beat.
    Fixed tokens + overlapN tokens, stride N−overlap The common default. Note the irony: overlap deliberately manufactures redundancy to avoid losing boundary context, and then you pay a pruner to remove it.
    Recursive structural split on paragraphs, then sentences, then words, until under the cap Respects the document's own boundaries. Strong, cheap default — this is what I would ship first.
    Semantic embed sentences, cut where consecutive-sentence similarity drops below a local percentile Boundaries land at genuine topic shifts. Costs an extra embedding pass, and the cut criterion is itself a threshold — so use a relative percentile, never an absolute value. Module 1's whole argument applies here too.
    Trap — overlap fakes the redundancy you are measuring

    Chunk with 20% overlap and adjacent chunks share text by construction, scoring artificially high cosine. Your effective rank is then depressed by an artifact of your own chunker, not by real redundancy in the source.

    The diagnostic signature: overlap redundancy is strictly between neighbouring indices, while genuine topical redundancy also appears between distant chunks. If all your high-similarity pairs are (i, i+1), you are measuring your chunker.

    Self-test — Module 5answer aloud, then open
    Why does similarity get less useful as chunks get longer?Answer

    Because the chunk embedding is a mean over its token vectors. A long chunk covering several topics averages them into one vector pointing at their centroid — and a centroid is by construction close to everything and specific to nothing.

    Two consequences. First, pairwise cosines drift upward and compress into a narrow band, so discrimination collapses — everything looks moderately similar to everything. Second, the spectrum flattens misleadingly, because each chunk now spans several real directions at once, so effective rank reports diversity that is really just blur.

    The practical rule: chunks should be roughly one idea, because one idea is what a single averaged vector can faithfully represent. If I had to pick a failure to watch for, it is the mean pairwise cosine creeping up as chunk size grows — that is the blur becoming measurable.

    You inherit a pipeline with 20% overlap. Effective rank is 40% below expectation. Is the pruner working? Answer

    Probably not — you are most likely measuring your own chunker. With 20% overlap, adjacent chunks literally share a fifth of their text, so they score high cosine by construction. That inflates the top eigenvalues and depresses effective rank whether or not the source document is actually repetitive.

    How I would diagnose it. Two checks. Re-chunk the same document with zero overlap and recompute effective rank — if it jumps back up, the redundancy was manufactured. And check where the high-similarity pairs sit: overlap redundancy is strictly between adjacent indices, while genuine topical redundancy also shows up between distant chunks. That adjacency signature is the tell.

    The fix depends on intent. If overlap exists to protect boundary context, keep it but measure the spectrum on non-overlapping chunks so your redundancy figure is honest. If it was cargo-culted from a tutorial default, remove it and let a recursive splitter respect real boundaries.

    Evaluation — the module you cannot skip

    Right now the claim "this pruner preserves answer quality" is unfalsifiable. Until a harness exists, every argument in this guide is a hypothesis. Assume the first question a sharp interviewer asks is "how do you know it works?"

    Real world — "my diet works"

    Someone says their diet works because they lost 4 kg. Compared to what? Doing nothing? A random diet? The season changing? Without a control you have a story, not a result.

    "My pruner retains 94% of effective rank" is the same story. It is a number about itself, not a comparison against an alternative.

    Step 1The one curve that matters

    x-axis: compression ratio (1 - kept_tokens / original_tokens) y-axis: task accuracy (measured on a real downstream task) accuracy |****----____ | \___ <- the KNEE: maximum compression | \__ before quality falls off | \_ +---------------------- compression 0% 90% Report the KNEE, not a single operating point.     Step 2The baselines you must beat, in order

    1. No pruning. The ceiling. If you match it at 50% compression, that is the headline.
    2. Random pruning to the same budget. The floor — and a shockingly strong baseline that embarrasses a lot of published work. If you cannot beat random, you have built nothing.
    3. Top-k by relevance. What everyone actually ships. This is the real competitor.
    4. Threshold dedup at its best cutoff, tuned on a dev split.
    Trap — tuning only your own method

    The most common way to fake a win is to tune your method carefully and compare it against someone else's default settings. Every baseline gets its own hyperparameter tuned on the same dev split. If threshold dedup has a cutoff, sweep it and report its best, not 0.8-because-that-is-typical.

    Reporting retained effective rank as proof the pruner works is writing the exam, sitting it, and marking it yourself. Greedy maximised that quantity, so a high score says "my optimiser optimised its objective" — which was never in doubt.

    Self-test — Module 6answer aloud, then open
    Design the experiment that would convince a skeptic.Answer

    Task and data: a multi-document QA set with known answers where retrieval genuinely returns redundant chunks — HotpotQA or MuSiQue for multi-hop, or a domain corpus with hand-written questions. Held out, never used for tuning.

    Independent variable: compression ratio, swept 0% to ~90%. Everything else fixed — same retriever, same top-N before pruning, same LLM, same prompt template, temperature 0.

    Arms: no pruning (ceiling), random-to-budget (floor), top-k by relevance, threshold dedup, and ours. Critically, each baseline gets its own hyperparameter tuned on the same dev split — comparing my tuned method against someone else's default is the standard way to manufacture a win.

    Dependent variables: answer accuracy (exact match and F1), plus latency and token cost, since efficiency is the entire point.

    Statistics: multiple seeds, confidence intervals, and a paired test across questions since every arm sees identical inputs. With a few hundred questions, differences under ~2 points are usually inside the noise — I would say so rather than claim them.

    What would falsify it: if random pruning tracks our curve, the spectral machinery contributes nothing and I should report that.

    Why is "retained effective rank" not a valid result?Answer

    Because it is the objective the selector maximised. Greedy facility location explicitly picks the subset that best covers the original set, which is nearly the same quantity — so a high retained effective rank tells you the optimiser worked, not that the pruner helps the task.

    It remains a legitimate diagnostic: if retained rank is low, something is broken. But validation requires a metric the pruner had no access to — downstream answer accuracy on held-out questions.

    The general principle is train/test separation applied to metrics rather than data: never score yourself on your own loss function. The same objection applies to reporting coverage, which is even more directly the thing greedy maximised.

    Scale and packaging

    Step 1Why n² is a wall, not a slope

    Real world — handshakes at a party

    Everyone shakes everyone's hand once. How many handshakes?

    10 people -> 45 handshakes 100 people -> 4,950 handshakes 1,000 people -> 499,500 handshakes 10,000 people -> 49,995,000 handshakes

    Ten times the guests, a hundred times the handshakes. Our similarity matrix is the handshake list: one entry per pair. That is why n² stops being an inconvenience and becomes a wall.

    Note the asymmetry, because it dictates every design decision: E grows linearly and stays small — a million chunks is only 1.5 GB. It is S that explodes. So the fix is always the same: never materialize S.

    Step 2The fixes, cheapest first

    TechniqueWhat it buys
    Upper triangle only2× memory. Does not change the asymptote — a constant-factor patch, not a fix.
    Blocked streamingProcess b rows at a time, reducing each block immediately to row-mean and row-max. Memory drops to O(nb). This is the workhorse.
    ANN neighbour graphHNSW or IVF-PQ for each chunk's top-m neighbours; keep a sparse graph at O(n m log n). Most of S is near zero anyway, so you lose almost nothing.
    Randomized truncated SVDSkips S entirely. O(ndk), linear in n. The right answer for the spectral path at any scale.
    Embedding cacheChunks repeat across requests, and the encoder forward pass usually dominates wall-clock. A content-hash keyed cache is often the single biggest practical speedup.
    Trap — optimising the wrong n²

    O(n²d) looks like the scary term, but at realistic n (hundreds) the matmul is microseconds while one encoder forward pass is tens of milliseconds. The n² memory wall is a real constraint at large n; the n² compute almost never is. Profile before optimising asymptotics — and say this in an interview, because it separates people who have shipped from people who have only analysed.

    Step 3What makes it a library rather than a repo

    • A narrow public API. Every symbol in __all__ is a promise you have to keep. Export less than you think.
    • Semantic versioning with a real deprecation path.
    • Typed, with py.typed so downstream type checkers actually see your annotations. A shipped package without that marker is untyped to everyone else no matter how annotated the source is.
    • Optional heavy dependencies. sentence-transformers drags in torch; an [embeddings] extra lets someone use the similarity and spectral maths with their own vectors.
    • CI across every supported runtime — which is why the pin is >=3.10,<3.14 and why that is stated in the README rather than discovered by a user.
    Self-test — Module 7answer aloud, then open
    A million chunks. Where does it break and what do you change?Answer

    E is fine — 1e6 × 384 float32 is 1.5 GB, large but ordinary, and linear. S is the break: 1e12 entries, 4 TB. It cannot exist, so every decision follows from never building it.

    Redesign: build an ANN index over E (HNSW), retrieve each chunk's top ~20 neighbours, and you have a sparse graph of 2×107 edges instead of 1012 cells. Run selection on that graph — greedy facility location only ever needs each chunk's best representative, which is almost always within its near neighbours, so the sparse graph loses very little.

    For spectral quantities, randomized truncated SVD directly on E at O(ndk) — linear in n, no S at any point. And cache embeddings by content hash, since at that scale the encoder pass dominates wall-clock.

    But I would question the premise. Pruning a million chunks into one context window is not a real scenario. The realistic architecture is hierarchical: ANN retrieval narrows to a few hundred candidates, then exact spectral pruning runs on those. Exact methods on a small candidate set beat approximate methods on the whole corpus — and noticing that the question contains a bad assumption is usually worth more than answering it as posed.

    Which single optimisation gives the biggest real-world win, and why is it not the linear algebra? Answer

    The embedding cache. Encoding is a transformer forward pass — tens of milliseconds per batch on GPU, far more on CPU — while the matmul for a few hundred chunks is microseconds. In production, chunks repeat heavily across requests (same documents, same knowledge base), so a content-hash keyed cache eliminates most of the actual cost.

    The broader point: complexity analysis tells you how things scale, not where the time goes today. O(n²d) is the frightening term on paper, but at n in the hundreds it is a rounding error next to one encoder pass. Profile first.

    I would keep the distinction sharp, though: the n² memory wall is real and hard at large n — 40 GB at n=100,000 — while the n² compute almost never binds. Those get conflated constantly.
