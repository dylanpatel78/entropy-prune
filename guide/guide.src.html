    Module 0Foundation

    Notation and the three shapes

    Almost every confusion in this library is a shape confusion, so fix the three objects first. Everything else is a transformation between them.

    E (n x d) the embedding matrix - one ROW per chunk, one COLUMN per dimension S (n x n) the similarity matrix - one cell per PAIR of chunks lam (n,) the spectrum - one number per independent DIRECTION embed multiply eigendecompose text ---------> E (n x d) ---------> S (n x n) ---------> lam (n,) | | +------------- SVD gives sigma ----------------+ (lam = sigma^2)

    Typical sizes: n is 20–500 context chunks, d is 384 for all-MiniLM-L6-v2. Hold onto the fact that n and d are independent — almost every interesting property depends on which is larger.

    Conventions used throughout

    SymbolMeansWhy it matters
    Eembedding matrix, unit-norm rows rows = chunks so pruning is row selection
    E.Ttranspose, shape (d, n) a free view in NumPy — no copy, just swapped strides
    @matrix multiply not *, which is per-cell and silently wrong
    S = E @ E.TGram matrix = cosine matrix true only because rows are unit length
    lam, sigmaeigenvalues of S, singular values of E lam = sigma^2; two views of one object
    kretained rank / chunk budget the one knob the whole library exists to set
    The load-bearing sentence

    Unit-norm rows make trace(S) = n, which makes lam/n a probability distribution, which makes Shannon entropy well-defined without any fudge factor. Normalization is not preprocessing — it is the coordinate system the library is defined in. If you remember one thing from this guide, remember this chain.

    Module 1Implemented & tested

    Embedding matrix and cosine similarity

    An encoder is a function: text of any length in, always the same number of floats out. Stack one row per chunk and you have E. The whole module is then two ideas — normalize the rows, then multiply the matrix by its own transpose.

    An embedding is a direction, not a magnitude

    Two chunks are two arrows from the origin. Similar meaning means the arrows point the same way, so measure the angle:

    dot(a, b) cos(angle) = --------------------- |a| * |b| dot(a,b) = a[0]*b[0] + a[1]*b[1] + ... + a[d-1]*b[d-1] |a| = sqrt(a[0]^2 + ... + a[d-1]^2) <- Pythagoras, d dimensions cos = +1.0 same direction identical meaning cos = 0.0 perpendicular unrelated cos = -1.0 opposite essentially never happens in practice

    Drag the sliders: the cosine is the angle, and nothing else.

    Notice what the length slider does

    Stretching b changes the dot product but never the cosine. That is the entire argument for normalizing. Embedding length correlates with chunk length, so ranking by raw dot product ranks long chunks first regardless of meaning.

    Worked example, small enough to verify by hand

    a = [3, 4] b = [4, 3] dot(a,b) = 3*4 + 4*3 = 24 |a| = sqrt(9+16) = 5 |b| = sqrt(16+9) = 5 cos = 24 / (5*5) = 0.96 -> 16.26 degrees apart

    Now the length trap, with real numbers. Searching for "interest rates":

    query = [1.00, 0.00] length 1.0 exact = [1.00, 0.00] length 1.0 short chunk, exactly on topic longdoc = [3.00, 9.54] length 10.0 long chunk, mostly off topic raw dot cosine exact 1.00 1.000 longdoc 3.00 0.300 <- raw dot ranks this FIRST

    Why normalizing first collapses the problem

    Divide every row by its own length and every chunk becomes an arrow of length exactly 1 — geometrically, every point is pushed onto the surface of a sphere. Then:

    if |a| = 1 and |b| = 1: cos = dot(a,b) / (1*1) = dot(a,b) so "dot every row with every row" IS the cosine matrix, which is exactly what matrix multiplication computes: S = E @ E.T (n,d) @ (d,n) -> (n,n)

    One multiply replaces n² dot products and n² divisions. Check an entry by hand with three chunks in 2-D:

    E = [[1.0, 0.0], chunk0 points right [0.8, 0.6], chunk1 points up-right [0.0, 1.0]] chunk2 points up S = E @ E.T = [[1.0, 0.8, 0.0], [0.8, 1.0, 0.6], [0.0, 0.6, 1.0]] S[1][2] = 0.8*0.0 + 0.6*1.0 = 0.6 <- chunk1 . chunk2
    The identity that kills the cosine-vs-Euclidean debate

    For unit vectors, distance(a,b)^2 = 2 - 2*cos(angle). As cosine rises, distance falls, always and smoothly. Ranking by cosine descending gives the identical ordering as ranking by Euclidean distance ascending. They are the same ranking — the choice only matters if you did not normalize.

    Four facts about S

    1. Symmetric. S[i][j] == S[j][i], because the angle between a and b is the angle between b and a. So you only ever need half of it.
    2. Unit diagonal. S[i][i] = 1; every chunk is perfectly similar to itself.
    3. Trace is exactly n. Follows from fact 2. Sounds trivial; it is the most useful fact in the library, because eigenvalues sum to the trace.
    4. Eigenvalues are never negative (positive semi-definite). Meaning: S is not an arbitrary grid of numbers, it is a geometrically realisable similarity structure. It cannot claim "A is like B, B is like C, but A is the opposite of C".
    Verified — real encoder output, 5 chunks

    Trap — the paraphrase scored 0.584

    Those first two sentences are genuine paraphrases of each other and they score 0.584, not 0.95. A "sensible" 0.8 dedup threshold catches neither. Absolute cosine values are not interpretable; only relative structure is. This single number is the whole motivation for Modules 3 and 4.

    Do not reach for the anisotropy argument here (the claim that embeddings bunch into a narrow cone, so baseline similarity is 0.1–0.4). That literature is about raw BERT and GPT-2. Sentence-tuned models are trained with in-batch negatives, which explicitly pushes unrelated pairs apart — measured baseline here is −0.001 to −0.12, essentially orthogonal. Use the calibration argument instead; it is true and checkable.

    The code, and the three lines people skip

    def l2_normalize(matrix, epsilon=1e-12):
    norms = np.linalg.norm(matrix, ord=2, axis=1, keepdims=True)
    return (matrix / np.maximum(norms, epsilon)).astype(np.float32, copy=False)

def cosine_similarity_matrix(vectors, assume_normalized=True):
    unit = vectors if assume_normalized else l2_normalize(vectors)
    gram = unit @ unit.T
    gram = np.clip(gram, -1.0, 1.0)      # 1
    gram = 0.5 * (gram + gram.T)         # 2
    np.fill_diagonal(gram, 1.0)          # 3
    return gram.astype(np.float32, copy=False)
    LineLooks likeActually prevents
    keepdims=Truea formatting flag shape (n,1) broadcasts per-row. Without it you get (n,), which NumPy right-aligns and divides column-wise. Errors when n≠d — and silently computes garbage when n=d.
    np.maximumsame as norms+eps a floor, not a bias. Adding epsilon perturbs every row's scale; maximum is a no-op on real norms and only guards true zeros.
    clip (#1)paranoia float32 error over 384 terms puts the diagonal at 1.0000001. Anything calling arccos downstream returns NaN and poisons everything.
    0.5*(S+S.T) (#2)a no-op on a symmetric matrix BLAS sums S[i][j] and S[j][i] in different orders, and float addition is not associative. eigvalsh assumes exact symmetry.
    fill_diagonal (#3)cosmetic this is what makes trace(S) = n exact, which is what makes Module 3's probability distribution exact. Drift here is a systematic error that grows with n.

    Self-test — Module 1answer aloud, then open
    Why L2-normalize at the embedding boundary instead of inside the cosine function where it is needed? Answer

    Three reasons, increasing in importance.

    Correctness. It becomes an enforced invariant of the type rather than a precondition every caller must remember. EmbeddingMatrix validates it once at construction, so no downstream function can silently receive raw vectors.

    Performance. Normalizing is O(nd) and cosine is called repeatedly — O(n) times in a greedy pruner — so normalizing per call turns a one-off into O(n²d) of duplicated work. It also lets the matmul drop every division.

    The real reason: the math downstream depends on it. Unit rows put exact 1s on the diagonal, so eigenvalues sum to exactly n, so lam/n is a probability distribution, so Shannon entropy is well-defined with no fudge factor. Normalization is the coordinate system, not a preprocessing step. I keep an assume_normalized=False escape hatch so the API stays honest about its precondition.

    10,000 chunks, 384 dimensions. Walk me through computing all pairwise cosines. What breaks? Answer

    Normalize rows once, then one GEMM: S = E @ E.T. Work is n*n*d = 3.8e10 multiply-adds — under a second on a GPU, a few seconds on CPU BLAS.

    Compute is not the constraint; memory is. S is 1e8 float32 entries = 400 MB. At n=100,000 it is 40 GB and does not fit. The method is O(n²) in space and simply stops working.

    Fixes, cheapest first: (a) store only the upper triangle — 2×, does not change the asymptote; (b) never materialize S — stream it in row blocks and reduce each block immediately to the statistics you need (row-mean, row-max), which is O(nb) memory in one pass; (c) replace exact all-pairs with ANN search (HNSW, IVF-PQ) and keep a sparse k-NN graph, turning O(n²) into about O(nk log n); (d) for the spectral path skip S entirely — randomized truncated SVD runs on E at O(ndk), linear in n.

    I would also flag dtype: float32, because the encoder's own noise is ~1e-3, so float64's extra digits are meaningless while doubling the memory bandwidth that actually bottlenecks a GEMM of this shape.

    A colleague ships E / np.linalg.norm(E, axis=1). Tests pass. What did they break?Answer

    They dropped keepdims=True, so norms has shape (n,) instead of (n,1). NumPy broadcasting aligns from the trailing axis, so (n,d) / (n,) is interpreted as dividing by a row vector — it normalizes down columns, not across rows.

    Why tests passed: when n != d this raises a ValueError and you catch it immediately. The danger is n == d — entirely possible, since d=384 and you might have 384 chunks — where it silently succeeds and returns wrong numbers. The rows are no longer unit length, so the diagonal of S is not 1, the trace is not n, and every entropy number downstream is quietly wrong.

    The lesson: assert the invariant, do not just compute it. Our EmbeddingMatrix.__post_init__ would have caught this at construction.

    Quant framing: how is S different from a correlation matrix of returns, and how does it fail? Answer

    Structurally it is the same object — symmetric, PSD, unit diagonal, trace n. The only difference is that correlation centers the columns first and this does not. So the same diagnostics apply: eigenvalue spectrum, condition number, effective rank.

    And it fails the same way, which is the failure that wrecks naive risk models: the matrix is estimated, not observed. When n is comparable to d, the small eigenvalues are estimation noise, and anything that inverts the matrix or leans on its bottom directions is fitting noise. Marchenko–Pastur tells you where the noise bulk ends as a function of n/d, which is a principled place to truncate.

    The reassuring part: this pruner only ever reads the top of the spectrum and discards the bottom — the numerically safe direction, the same logic as covariance shrinkage or using a factor model instead of the sample covariance. We never invert.

    The text-specific failure: absolute similarity levels are not interpretable (the 0.584 paraphrase), so only relative structure is actionable.

    Module 2Theory ahead of code

    SVD and subspace decomposition

    Cosine tells you about pairs. SVD tells you about the collection: which directions of meaning your context actually occupies, ranked by how much of it lies along each one.

    Every matrix is a rotate, then stretch, then rotate

    E = U Sigma V.T E (n x d) your data U (n x r) how much each CHUNK uses each direction ("chunk coordinates") Sigma (r x r) diagonal, sigma_1 >= sigma_2 >= ... >= 0 ("how much is there") V.T (r x d) the DIRECTIONS themselves, in embedding space ("semantic axes") r = min(n, d) for the thin SVD

    Read it right to left, the way the matrix acts on a vector: V.T rotates into a new basis, Sigma stretches each axis by a different amount, U rotates into the output space. The only part that destroys information is Sigma — and a sigma of zero destroys a whole direction.

    The columns of V are the thing to picture: each one is a direction in 384-dimensional meaning-space that your context uses, and sigma_i says how heavily. If your 50 chunks are all about the Fed, sigma_1 is huge and the rest are near zero.

    The bridge from Module 1
    S = E E.T = (U Sigma V.T)(U Sigma V.T).T = U Sigma V.T V Sigma U.T V.T V = I (V is orthonormal) = U Sigma^2 U.T so: eigenvalues of S == (singular values of E)^2 eigenvectors of S == left singular vectors of E

    Two views of one object. You can get sigma² from eigvalsh(S) at O(n³) or from svd(E) at O(n²d) — pick whichever of n, d is smaller.

    Eckart–Young: truncation is provably optimal

    Keep only the top k directions and you get E_k. The theorem says: of all matrices of rank k, E_k is the closest one to E — in both Frobenius and spectral norm. Not a heuristic. Optimal. And the error has a closed form:

    ||E - E_k||_F = sqrt( sigma_{k+1}^2 + sigma_{k+2}^2 + ... + sigma_r^2 ) i.e. the error is exactly the square root of the energy you threw away.

    This is why truncated SVD, and not some greedy feature-selection scheme, is the right primitive: you get the best possible rank-k summary and you know the error before you commit.

    SVD or PCA?

    PCA is the SVD of the mean-centered matrix. We use SVD directly, and the reasons matter:

    ReasonDetail
    Different question PCA asks "which directions do chunks vary in?" We ask "which directions do chunks occupy?" A chunk sitting exactly at the centroid is the most redundant chunk possible, yet centering turns it into the zero vector and PCA reads that as zero variance — i.e. unusual, keep it. Exactly backwards.
    Centering breaks the invariant Subtract the mean and rows are no longer unit length, so diag(S) != 1, so the trace is not n, so Module 3's probability distribution needs an arbitrary patch.
    Conditioning Forming E.T @ E to eigendecompose squares the condition number, costing half your significant digits. SVD works on E directly. Never explicitly form a covariance matrix if you can SVD the data.
    Rank deficiency SVD is defined and stable on singular matrices. When n > d ours is guaranteed singular.
    Trap — the nuance that separates good from great

    There is a real case for centering. The top singular direction of text embeddings is often just "the average direction all text points in", carrying little discriminative signal — which is why methods like all-but-the-top delete it deliberately. The complete answer is: "SVD on the uncentered matrix so the normalization invariant survives, but treat sigma_1 as a candidate nuisance direction and test empirically whether dropping it improves retrieval." That shows you know the theory, the literature, and that you would measure rather than assert.

    Randomized SVD, and why it is not cheating

    Full SVD costs O(n d min(n,d)) and computes all r directions. We only ever want the top k. The randomized algorithm:

    1. draw a random Gaussian matrix Omega (d x (k+p)) p = small oversample, ~5-10 2. sample the range Y = E @ Omega (n x (k+p)) 3. orthonormalize Q = qr(Y).Q Q spans ~the top-k range of E 4. project into that small basis B = Q.T @ E ((k+p) x d) <- tiny 5. exact SVD of the small matrix B = U_b Sigma V.T 6. lift back U = Q @ U_b cost O(n d k) instead of O(n d min(n,d)) -- LINEAR in n

    Why it works: multiplying by a random matrix almost surely hits the dominant subspace, because the large singular directions dominate the product. The error bound is probabilistic but extremely tight, and oversampling by ~10 makes failure vanishingly unlikely. This is the standard tool at scale, not an approximation of last resort.

    State Eckart–Young and explain why it matters for a pruner.Answer

    Of all matrices of rank at most k, the truncated SVD E_k = U[:,:k] Sigma[:k] V.T[:k] minimizes ||E - X|| in both the Frobenius and spectral norms. The minimum error is sqrt(sigma_{k+1}^2 + ... + sigma_r^2).

    Why it matters: it converts "which information should I throw away?" from a heuristic into a solved problem. Truncating the spectrum is provably the best rank-k summary available, and the closed-form error means I can pick k to hit a stated error budget before paying for the reconstruction. No other selection scheme gives you both optimality and a prior error estimate.

    The caveat I would volunteer: optimal in reconstruction error is not automatically optimal for downstream task accuracy. Those coincide only if the task depends on the embedding geometry the way the norm does, which is an empirical question — hence the evaluation harness in Module 6.

    SVD or PCA for this problem, and why? Answer

    SVD on the uncentered matrix. PCA is the same operation after subtracting the column mean, and that changes the question being asked: PCA finds directions of maximum variance about the centroid, we need directions the data occupies from the origin — the row space.

    The sharpest illustration: a chunk lying exactly at the centroid of all the others is the most redundant chunk in the set. Centering maps it to the zero vector, so PCA scores it as having no variance, which a selector reads as "unusual, keep it". Precisely inverted.

    Two supporting reasons: centering destroys the unit-norm invariant that makes trace(S) = n and hence makes the entropy stage exact; and the textbook PCA route of forming the covariance matrix squares the condition number, halving the significant digits, whereas SVD works on the data directly.

    And the nuance: the top direction of text embeddings is largely a common mean direction with little discriminative value, so there is a genuine argument for removing it — I would treat sigma_1 as a candidate nuisance direction and test it empirically rather than assume either way.

    Your matrix is 200,000 × 384 and you need the top 20 directions. How?Answer

    Randomized truncated SVD, never full SVD and never the Gram matrix.

    The Gram matrix is immediately out: S would be 2e5 × 2e5 = 4×1010 entries, about 160 GB in float32. It does not exist.

    Randomized SVD: sample the range with a random 384 × 30 Gaussian (k=20 plus ~10 oversample), giving a 200,000 × 30 product; QR that to get an orthonormal Q; project B = Q.T @ E, which is only 30 × 384; take the exact SVD of that tiny matrix and lift back. Cost is O(ndk) = 2e5 * 384 * 30, about 2×109 operations — seconds, and linear in n.

    Practical notes: one or two power iterations (Y = E @ (E.T @ Y)) sharpen the separation when the spectrum decays slowly; and since d = 384 < n, the rank is capped at 384 regardless, so I would sanity-check that k=20 actually captures the energy I need using the cumulative sigma² curve.

    Shannon entropy and effective rank

    You have n chunks. If three say the same thing you do not have three pieces of information, you have one. The question this module answers: how many genuinely distinct things do you actually have?

    The recipe

    1. eigenvalues of S lam = [lam_1, ..., lam_n] 2. they sum to n (unit diagonal) p = lam / n <- a probability distribution, FREE 3. Shannon entropy H = -sum( p_i * log(p_i) ) 4. back to a count effective_rank = exp(H)

    Step 2 is free only because we normalized in Module 1. That is the payoff of the invariant — no renormalization, no fudge factor.

    Why exp(H) is a count: entropy is maximized when p is uniform and minimized when it is concentrated. With m equal nonzero eigenvalues, H = log(m) exactly, so exp(H) = m. Exponentiating undoes the log and puts you back in units of "number of directions". This quantity is also called perplexity in language modelling and the effective number of bets in portfolio construction — same formula, three names.

    Choosing k without a magic constant

    Three defensible rules, in ascending sophistication:

    RuleHowTrade-off
    Energy threshold k = smallest k with cumulative sigma² ≥ 95% Simple and standard, but 95% is itself a magic constant — just a better-behaved one than a cosine cutoff.
    Effective rank k = ceil(exp(H)) Fully tuning-free and rotation-invariant. Can over-keep when the tail is long and flat, since many tiny eigenvalues still raise H.
    Noise floor Marchenko–Pastur: keep only eigenvalues above the random-matrix bulk edge, a function of n/d Principled — it asks "is this direction distinguishable from noise?" Needs n and d and assumes the noise model roughly holds.
    Trap — entropy in nats vs bits

    log base e gives nats; base 2 gives bits. It does not matter for exp(H) as long as you are consistent (2**H_bits == exp(H_nats)), but quoting "H = 2.77" without the unit is the kind of thing an interviewer will pick at. We use nats because np.log is natural log and exp inverts it directly.

    Second trap: p_i * log(p_i) is 0 * -inf = NaN at p_i = 0. The limit is 0, so you must mask zeros (p[p > 1e-12]). Since any corpus with n > d has exact zeros, this is not a hypothetical.

    Self-test — Module 3answer aloud, then open
    Why entropy over the spectrum rather than a cosine threshold? Give three independent reasons. Answer

    1. Thresholds do not transfer. Genuine paraphrases in our corpus score 0.584, so a "reasonable" 0.8 cutoff catches nothing. Any value you pick is fitted to one encoder on one corpus. Entropy is unitless and needs no constant.

    2. Pairwise rules are not transitive. If cos(a,b)=0.85, cos(b,c)=0.85, cos(a,c)=0.60, a threshold rule has no principled answer and the outcome depends on iteration order. Redundancy is a property of the set, and the spectrum measures the set — it asks about the span, not the pairs.

    3. Rotation invariance. H depends only on eigenvalues, and eigenvalues are invariant under E → EQ for orthogonal Q. Change encoder basis and H is unchanged; a threshold is not. That is what makes the criterion portable across models.

    A fourth if pressed: entropy gives a budget, not a filter. "Retain enough directions to cover 95% of the spectral entropy" maps onto a token budget; "drop pairs above 0.8" tells you nothing about how much you will keep until it has run.

    Prove that exp(H) equals m for m equally-weighted directions, and say why that makes it a "count". Answer

    Suppose m eigenvalues are equal and the rest are zero. By the trace identity they sum to n, so each nonzero lam_i = n/m and each p_i = lam_i/n = 1/m. Then:

    H = -sum_{i=1..m} (1/m) * log(1/m) = -m * (1/m) * log(1/m) = -log(1/m) = log(m) exp(H) = exp(log m) = m

    So a uniform spectrum over m directions returns exactly m. Because entropy is maximized by the uniform distribution and minimized (at 0) by a fully concentrated one, exp(H) interpolates smoothly between 1 and n. It is a continuous relaxation of matrix rank — identical to rank when the spectrum is flat, and strictly less whenever energy is unevenly spread. That continuity is what makes it usable as an objective; integer rank has zero gradient.

    A PM says "just keep the top 10 chunks by relevance score." Why is that different, and when are they right? Answer

    Relevance ranking is a pointwise criterion: it scores each chunk against the query independently. The failure is that the top 10 by relevance are frequently near-duplicates of each other — they all answer the same facet of the query, because the thing that makes one relevant makes its paraphrase relevant too. You spend the whole budget re-reading one idea and drop the chunk that covers the second facet.

    Effective rank is a set criterion: it asks how much distinct information the selected set spans. The two are orthogonal, and the right objective combines them — that is exactly what MMR and facility-location selection do in Module 4.

    When the PM is right: when the corpus has little redundancy, the pure relevance ranking is already near-diverse and the extra machinery buys nothing but latency. Our own corpus has effective rank 15.9 out of 20, i.e. only ~21% redundancy — at that level, plain top-k is a perfectly defensible baseline. Redundancy-aware selection earns its keep when retrieval pulls many overlapping chunks, which is the norm with overlapping windows or multi-query retrieval. The honest answer is "measure the effective rank of your retrieved set first; if it is close to k, top-k is fine."

    Module 4Theory ahead of code

    The pruning engine

    Modules 1–3 score. This module chooses. Given a token budget, which subset survives? That is a combinatorial optimization problem with its own theory, and it is where the strongest SWE interview signal lives.

    State the objective properly

    The natural objective is facility location (also called max-coverage): every chunk you drop should still be well-represented by something you kept.

    maximize f(P) = (1/n) * sum over all i in A of max over j in P of S[i][j] subject to sum of tokens(j) for j in P <= budget A = the full active set P = the kept subset

    Read the inner term: for chunk i, find its best representative in P. If i itself was kept, that is 1.0. If i was dropped but a near-duplicate survived, it is still high — nothing was really lost. If i was dropped and nothing like it survived, it is low, and the objective punishes you.

    Why greedy is good enough — and provably so

    Choosing the optimal subset is NP-hard. But f has two properties:

    • Monotone: adding a chunk never decreases coverage.
    • Submodular: diminishing returns. Formally, for P ⊆ Q and any x: f(P ∪ x) - f(P) ≥ f(Q ∪ x) - f(Q). Plainly: a chunk adds more when you have little than when you already have a lot.

    For monotone submodular functions under a cardinality constraint, the Nemhauser–Wolsey–Fisher theorem says simple greedy selection achieves at least (1 - 1/e) ≈ 63.2% of the optimum — and that bound is tight, i.e. no polynomial algorithm does better in general unless P = NP.

    Why this is the money answer in an interview

    "The problem is NP-hard, but the objective is monotone submodular, so greedy is a 1 - 1/e approximation by Nemhauser–Wolsey–Fisher, and that bound is tight." This tells the interviewer you recognized the problem class, know the guarantee, and know not to waste time searching for something better. Most candidates either brute-force it or hand-wave "greedy seems fine".

    greedy: P = {} while budget remains: pick the chunk x maximizing f(P + x) - f(P) <- marginal gain P = P + x cost O(k * n^2) with the running-best trick -- trivial for n in the hundreds

    The result that justifies the whole library

    Real 20-chunk corpus, budget k=8, greedy facility location versus threshold dedup at four cutoffs:

    Verified — greedy vs threshold, k=8, n=20

    greedy coverage[1, 6, 7, 10, 13, 17, 18, 19] 0.64017.776

    Look at which chunks each method picked, not just the scores. The corpus is ordered by topic: 0–4 monetary policy, 5–8 earnings, 9–12 risk methodology, 13–16 ML methodology, 17–19 unrelated.

    • Greedy picked [1, 6, 7, 10, 13, 17, 18, 19] — it lands in every topic cluster.
    • Threshold 0.70 picked [0,1,2,3,4,5,6,7] — the first eight chunks in index order, covering only the first two topics. It never reaches risk, ML, or the unrelated chunks at all.

    Threshold dedup is not a diversity algorithm. It is a scan that rejects anything too close to what it has already taken, so whatever comes first wins, and whole regions of meaning-space are never visited. Greedy is better on coverage and retained effective rank at every cutoff I tested, and it is not close.

    MMR: folding relevance back in

    Facility location maximizes diversity but ignores the query. Maximal Marginal Relevance interpolates:

    MMR: pick next x = argmax [ lambda * rel(x, query) - (1 - lambda) * max_{j in P} S[x][j] ] lambda = 1.0 -> pure relevance (top-k, ignores redundancy) lambda = 0.0 -> pure diversity (ignores the query entirely) lambda ~ 0.7 -> typical starting point; TUNE IT, do not inherit it

    lambda is an honest hyperparameter: it encodes a genuine preference about the relevance/diversity trade-off that no amount of math can settle for you. That is different from a cosine cutoff, which is a magic constant standing in for a measurement nobody made.

    Trap — token budgets break the clean guarantee

    The 1 - 1/e bound is for a cardinality constraint ("keep at most k items"). A real token budget is a knapsack constraint (items have different costs), and plain greedy loses the guarantee there. The fix is cost-benefit greedy: rank by marginal_gain / token_cost rather than marginal gain alone, which recovers a (1 - 1/e)-style bound via the Sviridenko/Khuller-Moss-Naor results. Knowing that the constraint type changes the guarantee is exactly the depth an interviewer is probing for.

    Self-test — Module 4answer aloud, then open
    Define submodularity and explain why it makes greedy the right choice here.Answer

    A set function f is submodular if for any P ⊆ Q and element x not in Q:

    f(P + x) - f(P) >= f(Q + x) - f(Q)

    That is diminishing returns: an element contributes more to a small set than to a large one. Our coverage objective has it because the inner term is a max — once some chunk already represents i well, a second similar chunk adds little.

    Why greedy: the exact problem is NP-hard, but for monotone submodular f under a cardinality constraint, Nemhauser–Wolsey–Fisher guarantees greedy reaches at least (1 - 1/e) ≈ 63.2% of the optimum, and that factor is tight — no polynomial-time algorithm beats it in general. So greedy is not a shortcut I am apologizing for; it is the best available guarantee, at O(k n²).

    I would add: with a real token budget the constraint becomes a knapsack, which breaks the plain bound. Ranking by gain / token_cost restores a comparable guarantee.

    Threshold dedup and greedy both kept 8 chunks. Greedy scored 0.640 coverage vs 0.507. Explain the mechanism, not just the number.Answer

    They are optimizing different things. Threshold dedup is a sequential filter: it walks the list in whatever order it arrives and rejects any chunk too similar to something already accepted. That makes the outcome a function of arrival order, not of the set's structure.

    In our corpus, chunks are grouped by topic, so at threshold 0.70 the filter accepted [0..7] — it filled the entire budget from the first two topics and never examined risk methodology, ML methodology, or the unrelated chunks. It is not that it judged them unimportant; it ran out of budget before reaching them.

    Greedy optimizes a global set objective. At every step it asks "which chunk most improves representation of everything I am not keeping?" — so after taking a policy chunk, every other policy chunk's marginal gain collapses and a risk chunk becomes the best pick. It naturally lands one chunk per cluster: [1, 6, 7, 10, 13, 17, 18, 19].

    The general lesson: a filter has no notion of what it has failed to cover; an objective does. That is why redundancy has to be posed as set selection rather than pairwise rejection.

    Your pruner drops a chunk that turns out to contain the one fact the user needed. How do you defend the design? Answer

    I would not defend it as "correct" — I would separate the two failure modes, because they have different fixes.

    Failure mode 1: the objective was right, the chunk was genuinely redundant, and the representative we kept did not carry that specific fact. This is the real limitation: coverage is measured in embedding space, and embeddings capture topical similarity, not factual equivalence. "Rates rose 25bp" and "rates rose 50bp" are highly similar vectors and completely different facts. No amount of spectral machinery fixes that, because the signal is not in the geometry. Mitigations: never prune below a floor, keep entity/number-bearing chunks preferentially, or run pruning only on chunks above a redundancy threshold rather than on everything.

    Failure mode 2: we pruned when we should not have pruned at all. If the retrieved set's effective rank is already close to k, there is no redundancy to remove and pruning is pure risk. The system should measure that and decline to act.

    And the honest framing: this is exactly why Module 6 (evaluation) is not optional. Without a harness measuring compression against task accuracy, "my pruner preserves quality" is an unfalsifiable claim. The defensible position is a measured operating point — "at 50% token reduction we lose 1.2% answer accuracy" — not an argument from theory.

    Module 5Planned

    Chunking and the input layer

    Everything upstream assumed "chunks" existed. They do not — you make them, and the choice quietly determines how well the rest works. This is the least mathematical module and the one most likely to be where your real wins are.

    The core tension

    SMALL chunks (1-2 sentences) LARGE chunks (paragraphs) + precise similarity + self-contained, readable + fine-grained pruning + fewer chunks -> cheaper n^2 - lose surrounding context - similarity gets mushy: a 300-word chunk - pronouns dangle ("it rose") averages many topics into one vector - n explodes -> n^2 hurts - pruning is coarse: all-or-nothing

    The deeper problem with large chunks is mean pooling. A chunk's embedding is the average of its token vectors, so a paragraph covering three topics produces a vector that points somewhere between all three — a centroid that matches nothing well. Similarity degrades toward the corpus mean as chunks grow. That is a direct argument for smaller chunks than intuition suggests.

    Strategies, worst to best

    StrategyMechanismVerdict
    Fixed character countsplit every N characters Splits mid-word and mid-sentence. Only acceptable as a baseline.
    Fixed tokens + overlapN tokens, stride N−overlap The common default. Overlap deliberately manufactures redundancy to avoid losing boundary context — note the irony: you then pay a pruner to remove it.
    Recursive structural split on paragraphs, then sentences, then words, until under the size cap Respects the document's own boundaries. Strong, cheap default.
    Semantic embed sentences, cut where consecutive-sentence similarity drops below a local percentile Boundaries land at genuine topic shifts. Costs an extra embedding pass, and the cut criterion is itself a threshold — use a relative percentile, not an absolute value.
    Trap — overlap double-counts in the spectrum

    If you chunk with 20% overlap, adjacent chunks share text by construction and score artificially high cosine. Your effective rank is then depressed by an artifact of your own chunker, not by real redundancy in the source. Either measure effective rank on non-overlapping chunks, or accept that some of what you are "pruning" is overlap you created. Being able to name this shows you understand the pipeline end to end.

    Self-test — Module 5answer aloud, then open
    Why does similarity get less useful as chunks get longer?Answer

    Because the chunk embedding is a mean over its token vectors. A long chunk covering several topics averages them into a single vector that points to their centroid — and a centroid is, by construction, close to everything and specific to nothing.

    Two consequences: pairwise cosines drift upward and compress into a narrow band (everything looks moderately similar, so discrimination collapses), and the spectrum flattens in a misleading way because each chunk now spans several real directions at once. The practical rule is that chunks should be roughly one idea, because one idea is what a single vector can faithfully represent.

    You inherit a pipeline with 20% overlap. Effective rank is 40% below expectation. Is pruning working? Answer

    Probably not — you are most likely measuring your own chunker. With 20% overlap, adjacent chunks literally share a fifth of their text, so they score high cosine by construction. That inflates the top eigenvalues and depresses effective rank regardless of whether the source document is actually repetitive.

    How I would diagnose it: re-chunk the same document with zero overlap and recompute effective rank. If it jumps back up, the "redundancy" was manufactured. Also check whether the high-similarity pairs are adjacent indices — overlap redundancy is strictly neighbouring, while genuine topical redundancy appears between distant chunks too. That adjacency signature is the tell.

    The fix depends on intent: if overlap exists to protect boundary context, keep it but measure the spectrum on non-overlapping chunks; if it is cargo-culted from a tutorial default, remove it and let the recursive splitter respect real boundaries instead.

    Evaluation — the module you cannot skip

    Right now the claim "this pruner preserves answer quality" is unfalsifiable. Until a harness exists, every theoretical argument in this guide is a hypothesis. Assume the first question a sharp interviewer asks is "how do you know it works?"

    The one curve that matters

    x-axis: compression ratio (1 - kept_tokens / original_tokens) y-axis: task accuracy (measured on a real downstream task) accuracy |****----____ | \___ <- the knee: max compression | \__ before quality falls off | \_ +---------------------- compression 0% 90% Report the KNEE, not a single operating point. A pruner is a curve, not a number.

    Plus a baseline set you must beat, in this order: no pruning (the ceiling), random pruning to the same budget (the floor — and a shockingly strong baseline that embarrasses a lot of published work), top-k by relevance, and threshold dedup. If you cannot beat random, you have built nothing.

    Metrics, and what each hides

    MetricMeasuresBlind spot
    Recall@kdid the needed chunk survive? ignores ordering and ignores whether the model could use it
    nDCGrecall weighted by position needs graded relevance labels, which are expensive and subjective
    Answer accuracy (F1 / exact match)end-to-end task success conflates pruner quality with the LLM's own variance
    Retained effective rankinformation kept, by our own measure circular — it is the objective we optimized. Useful as a diagnostic, never as validation.
    Trap — do not validate on your own objective

    Reporting "we retained 94% of effective rank" as evidence the pruner works is circular reasoning: effective rank is what greedy maximized. It is a diagnostic, not a result. Validation has to come from a metric the pruner did not optimize — downstream answer accuracy on held-out questions. Stating this unprompted is a strong signal of experimental maturity.

    Self-test — Module 6answer aloud, then open
    Design the experiment that would convince a skeptic.Answer

    Task and data: a multi-document QA set with known answers where retrieval genuinely returns redundant chunks — HotpotQA or MuSiQue for multi-hop, or a domain corpus with hand-written questions. Held out, never used for tuning.

    Independent variable: compression ratio, swept from 0% to ~90%. Everything else fixed — same retriever, same top-N before pruning, same LLM, same prompt template, same decoding temperature (ideally 0).

    Arms: no pruning (ceiling), random-to-budget (floor), top-k by relevance, threshold dedup at its best cutoff, and ours. Critically, each baseline gets its own hyperparameter tuned on a dev split — comparing my tuned method against someone else's default is the most common way to fake a win.

    Dependent variable: answer accuracy (exact match and F1), plus latency and token cost, since the whole point is efficiency.

    Statistics: multiple seeds, report confidence intervals, and use a paired test across questions since the arms see identical inputs. With a few hundred questions, differences under ~2 points are usually inside the noise — say so rather than claiming them.

    What would falsify it: if random pruning tracks our curve, the spectral machinery is not contributing and I should say so.

    Why is "retained effective rank" not a valid result?Answer

    Because it is the objective the selector maximized. Greedy facility location explicitly picks the subset that best covers the original set, which is almost the same quantity — so reporting high retained effective rank says "my optimizer optimized its objective", which was never in doubt.

    It is a legitimate diagnostic: if retained rank is low, something is broken. But validation requires a metric the pruner had no access to — downstream answer accuracy on held-out questions. The general principle is train/test separation applied to metrics rather than data: never score yourself on your own loss function.

    Scale and packaging

    Everything so far assumed S fits in memory. Here is exactly where that stops being true.

    The n² wall, float32
    nE (n×384) S (n×n)verdict
    1,0001.5 MB4 MB trivial
    10,00015 MB400 MB fits, but you feel it
    50,00077 MB10 GB most machines are out
    100,000154 MB40 GB does not fit
    1,000,0001.5 GB4 TB absurd

    Note the asymmetry: E grows linearly and stays tiny — a million chunks is only 1.5 GB. It is S that explodes. So the fix is always the same: never materialize S.

    TechniqueWhat it buys
    Upper triangle only2× memory. Does not change the asymptote — a constant-factor patch, not a fix.
    Blocked streamingProcess b rows at a time, reduce each block immediately to row-mean and row-max. Memory drops to O(nb). This is the workhorse.
    ANN neighbour graphHNSW or IVF-PQ for each chunk's top-m neighbours; keep a sparse graph. O(n m log n). Most of S is near zero anyway, so you lose almost nothing.
    Randomized truncated SVDSkips S entirely. O(ndk), linear in n. The right answer for the spectral path at any scale.
    Embedding cacheChunks repeat across requests; the encoder forward pass usually dominates wall-clock. Content-hash keyed cache is often the single biggest practical speedup.

    What makes it a library rather than a repo

    • A narrow public API. Every symbol in __all__ is a promise you have to keep. Export less than you think.
    • Semantic versioning with a real deprecation path.
    • Typed, with py.typed so downstream type checkers actually see your annotations — a shipped package without that marker is untyped to everyone else, no matter how annotated the source.
    • Optional heavy dependencies. sentence-transformers pulls in torch; an [embeddings] extra lets someone use the similarity and spectral math with their own vectors.
    • CI across every supported runtime, which is why the version pin is >=3.10,<3.14 and stated in the README.
    Self-test — Module 7answer aloud, then open
    A million chunks. Where does it break and what do you change?Answer

    E is fine — 1e6 × 384 float32 is 1.5 GB, large but ordinary, and it grows linearly. S is the break: 1e12 entries, 4 TB. It cannot exist, so every design decision follows from never building it.

    Redesign: build an ANN index over E (HNSW) and retrieve each chunk's top ~20 neighbours, giving a sparse graph of 2×107 edges instead of 1012 cells. Run selection on that graph — greedy facility location only ever needs each chunk's best representative, and that is almost always within its near neighbours, so the sparse graph loses very little.

    For the spectral quantities, use randomized truncated SVD directly on E at O(ndk) — linear in n, no S at any point. And cache embeddings by content hash, since at that scale the encoder forward pass, not the linear algebra, dominates wall-clock.

    I would also question the premise: pruning a million chunks in one context window is not a real scenario. The realistic shape is a hierarchy — ANN retrieval narrows to a few hundred candidates, then exact spectral pruning runs on those. Exact methods on a small candidate set beat approximate methods on the whole corpus.

    Which single optimization gives the biggest real-world win, and why is it not the linear algebra? Answer

    The embedding cache. Encoding is a transformer forward pass — tens of milliseconds per batch on GPU, far more on CPU — while the matmul for a few hundred chunks is microseconds. In production, chunks repeat heavily across requests (same documents, same knowledge base), so a content-hash keyed cache eliminates most of the actual cost.

    The broader point: O(n²d) looks like the scary term in the complexity analysis, but at realistic n (hundreds) it is a rounding error next to one encoder pass. Profile before optimizing the asymptotics. The n² memory wall is a real constraint at large n; the n² compute almost never is.
